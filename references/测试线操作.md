# 测试线操作

测试单与用例的写入，走与其他实体相同的「预览 → 用户确认 → 单次写入 → 回查」两步流程。

```text
python <技能目录>/scripts/zentao.py testtask-prepare   --plan <plan路径>
python <技能目录>/scripts/zentao.py testtask-submit    --review <完整摘要> --confirm <同一完整摘要>
python <技能目录>/scripts/zentao.py testcase-prepare   --plan <plan路径>
python <技能目录>/scripts/zentao.py testcase-submit    --review <完整摘要> --confirm <同一完整摘要>
```

## 计划格式

`testtask` 与 `testcase` 都支持 `create` 与 `update`，修改时编号键与实体同名。

```text
{"action":"create","fields":{"name":"V1.2 回归测试","begin":"2026-10-16","end":"2026-10-20","project":1,"product":1,"execution":2,"build":3,"owner":"your-account"}}
{"action":"update","testtask":1001,"fields":{"name":"V1.2 回归测试（第二轮）","end":"2026-10-25"}}
{"action":"create","fields":{"product":1,"title":"登录页验证码校验","type":"feature","pri":3,"steps":[{"desc":"打开登录页","expect":"显示验证码"},{"desc":"输入错误验证码","expect":"提示错误"}]}}
{"action":"update","testcase":2001,"fields":{"pri":2,"precondition":"账号已注册"}}
```

**修改测试单时只给要改的项即可**——脚本会先读当前记录，把其余字段一并带上（原因见下面第 2 条）。

## 端点与字段

| 实体 | 新建 | 修改 | 必填 |
|---|---|---|---|
| 测试单 | `POST v1/projects/{project}/testtasks` | `PUT v2/testtasks/{id}` | project、product、build、name、begin、end（创建另需 execution） |
| 用例 | `POST v1/testcases` | `PUT v1/testcases/{id}` | product、title、type、pri、steps（仅创建） |

- **测试单字段**：project、product、execution、build、name、begin、end、owner、type、pri、status、desc。
  - `status` 取 `wait`（未开始）、`doing`（进行中）、`done`、`blocked`（被阻塞）。**`done` 在页面上显示为「已关闭」**——改成 `done` 就是关闭测试单，开始用 `doing`，重新打开用 `wait`。
  - ⚠️ **不要用 `closed`**。它对测试单是死状态：写入后记录会从所有 v1 列表里消失，页面状态列也渲染异常（看着像没关闭）。正常关闭的测试单 `closedBy` / `closedDate` 本来就是空的，这两个字段对测试单没有意义，不用管。
  - `execution` 可留空；`type` 可传字符串或数组（如 `"integrate"` 或 `["integrate","system"]`），常见取值 `integrate`、`system`、`acceptance`、`performance`、`safety`。
- **用例字段**：product、title、type、pri、steps、module、stage、story、precondition；修改另支持 branch、script、keywords。
- **用例步骤**是数组，每项 `{"desc":"操作","expect":"预期","type":"step"}`；`type` 取 `step`、`item`、`group`，不写默认 `step`。**修改时给出 steps 会整体替换原步骤**，不给则保持原样。
- **用例类型**常见取值：`feature`、`performance`、`interface`、`install`、`security`、`other`；脚本不硬校验，以站点实际接受为准。

## 五条与别处不同的接口行为

1. **测试单的修改只在 v2**。v1 的条目只实现 `get()` 与 `delete()`，`PUT v1/testtasks/{id}` **返回 200 且响应为空**——静默假成功，比 4xx 更容易骗过人。真接口是 `PUT v2/testtasks/{id}`，返回 `{"status":"success","message":"保存成功"}`。所以脚本**用 v2 改、用 v1 读**。
2. **v2 的修改是整份覆盖，不是局部更新**。没传的字段会被**静默清空**（实测：只传名称与日期改个名字，`execution` 与 `owner` 当场被抹成 0 与空）。因此脚本在提交前会把当前记录里的其余可写字段一并带上，用户只给要改的项。**这也是为什么不要自己拼这个请求**——漏一个字段就是丢一个字段。
3. **测试单的 `project` 只认路径参数**（源码读 `param('project')`），放 JSON body 里会被忽略并报 `need project id!`——与执行创建同一个坑；脚本已走 `v1/projects/{project}/testtasks`。
4. **用例的 `product` 必须放请求体**：`POST v1/testcases` 可用，而路径式 `POST v1/products/{id}/testcases` 返回 **403**（两个路由指向同一个条目类，但权限判定不同）。
5. **`closed` 是死状态，`done` 才是关闭**。写成 `closed` 后记录从所有列表消失、页面显示异常；而 `closedBy` / `closedDate` / `realFinishedDate` 三个字段无论怎么传都**写不进去**（返回「保存成功」但实际被忽略）。用 `done` 关闭则页面显示「已关闭」、记录留在列表里，只是「实际完成日期」为空——不影响使用。

## 关联编号会先预检

测试单的四层关联最容易被服务端用一句 `error execution id!` 打发，所以脚本在预览阶段先自己查清：

- 项目、产品、执行必须存在（编号写错时接口未必报错）；
- **执行必须属于该项目**（查执行详情的 `project`）；
- **执行必须已关联该产品**（查执行详情的 `products`）；
- **构建必须属于该项目**，且**属于该产品**（查项目构建列表并按 `product` 字段核对）。

任何一条不满足都当场报错并说明原因，不发写入请求。**修改时只在动了关联字段时才重查**——历史测试单未必还满足当年的约束，否则改个名字都会被拦住。

## 权限

- **测试单**：写权限通常属测试角色或管理员。
- **用例**：写权限通常属管理员、产品经理或测试角色。

没有权限时接口返回 HTTP 403，脚本会明确提示「当前账号没有××的写权限，请管理员授权」并要求如实转达，**不要压缩成「操作失败」**。

> 判断是否有权限要看**补齐必填之后**的响应：缺 `product` 时 `POST v1/testcases` 返回的是 400「Need product id.」，**必填校验先于权限检查**，只看这个 400 会误判成「有权限」。

## 写入后的处理

- 写入前重新读取实时详情与预览指纹比对；预览后被人改过就拒绝写入并要求重新预览。
- 写入后只核对**本次请求的字段**；用例的步骤不逐条比对（接口对步骤字段的命名在版本间不一致，核对必然误报）。
- 结果不明时保留收据并**禁止重发**，只能只读回查。同一份预览不允许执行两次。
- **不提供删除测试单或用例**。
