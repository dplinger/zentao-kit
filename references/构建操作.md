# 新建与修改构建

构建是发版流程的枢纽对象：Bug 的「解决版本」、测试单的「构建」都要指向它。本流程只做新建与修改，不提供删除。

## 对话流程

1. 登录后确认用户要新建还是修改构建。不采集聊天记录、不套用每日工时分配。
2. 新建先查 `projects`、`executions --project <编号>`、`query --entity products`，让用户明确**项目、产品、执行**三者；修改先确认构建编号，可用 `builds --project <编号>` 或 `builds --execution <编号>` 列出可选项，查不到不能猜编号。
3. 名称、创建人、打包日期由用户给出或据其意图拟定；未指定时可在预览中建议指派当前登录账号、日期取当天。日期必须是 `YYYY-MM-DD`，不能沿用示例或编造。
4. 在本次内部运行目录保存构建计划 JSON，调用 `build-prepare --plan <绝对路径>`。预览展示动作、项目/执行、字段中文名与修改前后值。
5. 用户确认预览后，执行 `build-submit --review <摘要> --confirm <同一摘要>`，回复构建编号、名称与链接。
6. 接口超时、返回失败或回查不一致时停止，不自动重发、不另建计划重试。操作记录位于 `~/.zentao-worklog/actions/`，保留用于核对；成功后自动清理预览与收据。

## 接口与计划字段

鉴权由客户端携带当前用户 Token。以下接口前缀均为站点 `/api.php/`。

| action | 方法与路径 | fields |
|---|---|---|
| create | POST v1/projects/{project}/builds | execution、product、name、builder、date；可选 branch、scmPath、filePath、desc |
| update | PUT v1/builds/{id} | 只在计划里写用户要改的字段；脚本从实时详情补齐其余字段，完整发送，保留原值 |

create 计划还需 `project` 编号——它**只认路径参数**，写进 fields 无效，且用于校验执行归属。修改需 `build` 编号。所有计划均包含 `action` 和 `fields`。

```json
{
  "action": "create",
  "project": 1,
  "fields": {
    "product": 2,
    "execution": 3,
    "name": "用户确认的构建名称",
    "builder": "当前登录账号",
    "date": "2026-01-01"
  }
}
```

```json
{
  "action": "update",
  "build": 4,
  "fields": {"desc": "只写要改的项"}
}
```

示例仅演示结构，不代表操作指令。`builder` 填**登录账号**而不是姓名；`branch` 是分支编号，多分支产品可用 0 表示主干。

## 三条必须知道的行为

**必填五项少一个即失败**：`execution`、`product`、`name`、`builder`、`date`。缺项时服务端只回笼统错误，用户难以定位，**脚本在预览阶段就会拦下并说明缺哪项**。

**执行必须属于该项目**：跨项目的执行/项目组合，服务端只回 `error execution id!` 之类，脚本已改为预览阶段先核对执行详情里的 `project`，不一致直接停止。

**创建成功可能返回空响应体**：部分版本创建构建会返回 `201` 且响应体为空，**这不等于失败**。脚本会按「同项目 + 同执行 + 同名称 + 同日期」唯一命中回查新记录：唯一命中即认定成功；零条报未找到；多条报无法确定。此时**不要重发请求**，先只读核对构建列表。

## 修改的语义

`PUT v1/builds/{id}` 对**未传字段保留旧值**（与测试单的 `PUT v2/testtasks/{id}` 整份覆盖语义相反）。脚本仍会从当前详情补齐必填项再发送，原因不是接口需要，而是防服务端行为变化时把构建改坏。

修改时**所属项目由记录本身固定，所属执行在页面上是只读的**——页面明确提示「已关联需求、Bug 或测试单的构建不能修改所属产品」「提交测试单的构建不能修改所属迭代」，脚本的漂移检测也盯这三项（`project`、`product`、`execution`），一旦被意外改动即报错并保留收据。

## 与其他对象的关系

- **构建不是版本号的同义词**：禅道另有虚拟版本 `trunk`（主干），它不在这张表里，只能从 Bug 解决表单读到。新建构建不会影响 `trunk` 的可用性。
- Bug 的解决版本要用 `resolve-builds --bug <编号>` 取合法取值与推荐项，其中已按该 Bug 的影响版本自动挑选，不要自己拼。
- 测试单必须挂构建，可用 `builds --project <编号>` 取可选项。

## 权限

新建与修改构建通常需要开发或测试角色权限。遇到 403 如实转达脚本给出的授权提示，不要压缩成「操作失败」，也不要改用裸接口绕过。
