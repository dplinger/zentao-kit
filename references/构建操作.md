# 新建与修改构建

构建是发版流程的枢纽对象：Bug 的「解决版本」、测试单的「构建」都要指向它。本流程只做新建与修改，不提供删除。

所有写操作走 **v2 接口**（`POST v2/builds`、`PUT v2/builds/{id}`、`GET v2/builds/{id}`），不用 v1。

## 对话流程

1. 登录后确认用户要新建还是修改构建。不采集聊天记录、不套用每日工时分配。
2. 新建先查 `query --entity products`、`executions --project <编号>`，让用户明确**产品、执行**两个编号；修改先确认构建编号，可用 `builds --execution <编号>` 列出现有构建，查不到不能猜编号。
3. 名称、构建者、打包日期由用户给出或据其意图拟定；未指定时可在预览中建议指派当前登录账号、日期取当天。日期必须是 `YYYY-MM-DD`，不能沿用示例或编造。
4. 在本次内部运行目录保存构建计划 JSON，调用 `build-prepare --plan <绝对路径>`。预览展示动作、执行/产品、字段中文名与最终提交值。
5. 用户确认预览后，执行 `build-submit --review <摘要> --confirm <同一摘要>`，回复构建编号、名称与链接。
6. 接口超时、返回失败或回查不一致时停止，不自动重发、不另建计划重试。操作记录位于 `~/.zentao-worklog/actions/`，保留用于核对；成功后自动清理预览与收据。

## 接口与计划字段

鉴权由客户端携带当前用户 Token。接口前缀为站点 `/api.php/`。

| action | 方法与路径 | 必填字段 |
|---|---|---|
| create | POST v2/builds | `executionID`、`product`、`name`、`system`、`builder`、`date` |
| update | PUT v2/builds/{id} | **无**——局部更新，传什么改什么 |

**只提交这六项**。`branch`、`scmPath`、`filePath`、`desc` 都不是必填，不指定就不发——多传一个字段就多一处出错点。`branch` 仅在用户明确要求指定分支时透传。

⚠️ **同一个「执行」在两个接口里字段名不一样**：创建写 `executionID`，修改写 `execution`。计划里一律写 `execution`，脚本只在创建发送时改名为 `executionID`；修改时保持 `execution` 原名。搞反了要么报错，要么把执行写成 0。

`builder` 填**登录账号**而不是姓名。

```json
{
  "action": "create",
  "fields": {
    "product": 2,
    "execution": 3,
    "name": "用户确认的构建名称",
    "builder": "当前登录账号",
    "date": "2026-01-01"
  }
}
```

```json
{
  "action": "update",
  "build": 4,
  "fields": {"desc": "只写要改的项"}
}
```

示例仅演示结构，不代表操作指令。`system`（所属应用）通常不用写：脚本按产品自动补，产品下有多个应用时会在预览里列出来让用户指定。

## 四条必须知道的行为

**必填六项，缺一项服务端就拒**：`executionID`、`product`、`name`、`system`、`builder`、`date`。缺项时服务端返回的是结构化错误（`{"result":"fail","message":{…}}`），脚本在预览阶段就拦下并说明缺哪项。

**「所属应用」`system` 是必填，且按产品取值**：候选来自页面保存用的同一接口 `/build-ajaxGetSystemList-{产品编号}.json`，返回 `[{"text":"管控中心","value":2}]`。脚本在产品只有一个候选时自动填上，多个时列出全部候选让用户选。**这个字段必须落库**——`system=0` 的构建属于「未分类」，会被构建列表过滤掉，页面上看不见。

**为什么不用 v1**：`POST v1/projects/{id}/builds` 根本写不进 `system`，建出来的构建恒为 `system=0`。它会连带出一串误判：列表查不到 → 以为没建成 → 以为没权限（2026-11-12 的真实事故，台账 D17）。v2 把 `system` 列为必填并真正落库，这条路才通。

**结果不明确时只读核对，不要重发**：v2 正常会返回结构化结果，但万一遇到异常空响应，**空响应不等于失败，也不等于可以重发**。脚本回查走 `GET v2/executions/{执行}/builds`，按「同执行 + 同名称 + 同日期」取编号最大的一条。v2 建出来的构建 `system` 有值，不会被列表过滤，所以找得回来。

## 修改的语义

`PUT v2/builds/{id}` 是**局部更新**：传什么改什么，没传的字段原样保留。实测只传 `name` 一项、连其他五项必填都不带，接口照样返回「保存成功」，产品、执行、所属应用、构建者、日期、描述全部保留。

**所以修改时不要铺旧值**——脚本只发用户给出的字段，不补齐、不兜底。这与 `PUT v2/testtasks/{id}`（测试单，整份覆盖、不传即清空）的语义**正好相反**，两个实体不能共用一套策略。

修改时**所属项目由记录本身固定，所属执行在页面上是只读的**——页面明确提示「已关联需求、Bug 或测试单的构建不能修改所属产品」「提交测试单的构建不能修改所属迭代」。脚本的漂移检测盯 `product`、`execution` 两项：只改名称却把执行带跑偏了，会报错并保留收据。

## 与其他对象的关系

- **构建不是版本号的同义词**：禅道另有虚拟版本 `trunk`（主干），它不在这张表里，只能从 Bug 解决表单读到。新建构建不会影响 `trunk` 的可用性。
- Bug 的解决版本要用 `resolve-builds --bug <编号>` 取合法取值与推荐项，其中已按该 Bug 的影响版本自动挑选，不要自己拼。
- 测试单必须挂构建，可用 `builds --execution <编号>` 取可选项。

## 权限

新建与修改构建通常需要开发或测试角色权限。遇到 403 如实转达脚本给出的授权提示，不要压缩成「操作失败」，也不要改用裸接口绕过。
