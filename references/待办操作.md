# 待办操作

用「预览 → 用户确认 → 单次写入 → 回查」两步完成待办的新建、修改、完成和激活。全程只用 v1 接口，无第三方依赖。

```text
python <技能目录>/scripts/zentao.py todo-prepare --plan <plan路径>     # 只读，生成预览
python <技能目录>/scripts/zentao.py todo-submit --review <完整摘要> --confirm <同一完整摘要>
```

## 计划格式

`create` 不用编号；`update`/`finish`/`activate` 用 `todo` 指定待办编号。`finish` 与 `activate` 是单一动作，`fields` 留空对象即可。

```text
{"action":"create","fields":{"name":"整理本周工时","pri":2,"date":"2026-10-16","begin":"09:00","end":"09:30","desc":"把上周的工时补齐"}}
{"action":"update","todo":3,"fields":{"name":"整理本周工时（改）","pri":1,"status":"doing"}}
{"action":"finish","todo":3,"fields":{}}
{"action":"activate","todo":3,"fields":{}}
```

## 各操作的端点与字段

| 操作 | 方法与本路径（接 `/api.php/`） | 允许的字段 | 必填 |
|---|---|---|---|
| 新建 | `POST v1/todos` | name、desc、date、begin、end、pri、private | **name** |
| 修改 | `PUT v1/todos/{id}` | 同上再加 status（仅 `wait`/`doing`） | 至少一个字段 |
| 完成 | `GET v1/todos/{id}/finish`（有副作用） | 无 | 无 |
| 激活 | `GET v1/todos/{id}/activate`（有副作用） | 无 | 无 |

- **完成与激活是 GET 请求**，这不是笔误：两个条目类（`todofinish.php`、`todoactivate.php`）只实现了 `get()`。也就是说**这两个 GET 带副作用，调用即写入**，绝不能当查询重试。
- 状态取值：`wait`（未开始）、`doing`（进行中）、`done`（已完成）、`closed`（已关闭）。
- `begin` / `end` 接受 `HH:MM`，服务端去掉冒号后按四位数存储（`09:30` → `0930`）；`24:00` 是禅道表示「整天」的默认值。开始时间不得晚于结束时间。
- `pri` 为 1 至 4；`private` 是布尔（是否私有）；`desc` 是富文本，纯文本会自动包成段落，已含 HTML 标签的原样保留。

## 状态前置条件（预览阶段就拦住）

| 操作 | 允许的当前状态 |
|---|---|
| 修改 | `wait`、`doing` |
| 完成 | `wait`、`doing` |
| 激活 | `done`、`closed` |

- 已完成的待办要改内容，先 `activate` 回到「未开始」再改。
- 完成只能走 `finish`：用 `PUT` 直接把 status 改成 `done` 不会写完成时间，属半吊子写入，脚本会拒绝。
- 修改待办时把 status 设为 `wait`/`doing` 是允许的（开始或暂停），但设成 `done`/`closed` 会被拒绝。

## 两件刻意不做的事

- **不关闭待办**。接口没有关闭路由：`config/apiv1.php` 只注册了 `/todos`、`/todos/:id`、`/todos/:id/finish`、`/todos/:id/activate`。用 `PUT` 改 status 会绕过模型的 `close()`（它负责写 `closedBy`/`closedDate` 并改 `assignedTo`），数据会不一致。
- **不操作关联型待办**。由任务、需求、Bug 等对象生成的待办（`type` 不是 `custom`）归来源对象管，脚本在预览阶段就拒绝修改，并提示到来源对象页面处理。新建也只做个人事务型待办。

## 权限

待办属个人事务，一般账号都有读写权限。若仍返回 403，脚本会明确说明「当前账号无权操作待办，请管理员检查该账号的待办权限」，**请如实转达**，不要压缩成「操作失败」。

## 写入后的处理

- 写入前重新读取待办详情，与预览时的指纹比对；**预览后有人改过就拒绝写入**并要求重新预览。
- 写入后重新读取详情核对；修改时还会逐项核对**未请求的字段是否被改动**（服务端用旧值兜底，发现漂移就报出具体字段名）。完成要求状态变为 `done` 且完成时间已写入，激活要求状态回到 `wait`。
- 结果不明（超时、响应异常）时保留收据并**禁止重发**，只能只读回查。同一份预览不允许执行两次。
- 不提供删除待办的能力。

## 验证状态

新建、修改、完成、激活四条路径均已在本机真实实例上端到端跑通并回查通过（含状态前置、防重、确认串校验与错误分支）。
