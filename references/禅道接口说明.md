# 禅道接口说明

依据用户的《禅道自动化填写日志》和 Apifox 示例。站点从个人配置或已验证登录状态读取；不复制原文中的账号或令牌。路径均接在站点 /api.php/ 后。

| 操作 | 方法及路径 | 依据 |
|---|---|---|
| 鉴权 | POST v2/users/login | 用户示例；[官方V2登录](https://www.zentao.net/book/api/post-users-login-2142.html) |
| 新建任务 | POST v2/tasks | 用户原始 Apifox 示例 |
| 修改任务 | PUT v2/tasks/{taskID} | 用户补充示例 |
| 完成任务 | PUT v2/tasks/{taskID}/finish | 用户原始示例 |
| 关闭任务 | PUT v2/tasks/{taskID}/close | 用户原始示例 |
| 当前身份 | GET v1/user | 用户文档，读取 profile.account |
| 项目列表 | GET v1/projects | 实测查询路径 |
| 执行列表 | GET v2/projects/{projectID}/executions | 用户示例 |
| 任务列表 | GET v2/executions/{executionID}/tasks | 用户最新示例，优先于旧笔记v1 |
| 任务详情 | GET v1/tasks/{taskID} | 官方v1路径，需实例只读验证 |
| 日志列表 | GET v1/tasks/{taskID}/estimate | 用户示例；[官方获取任务日志](https://www.zentao.net/book/api/1199.html) |
| 批量登记 | POST v1/tasks/{taskID}/estimate | 用户企业版10.6之后示例；[官方添加任务日志](https://www.zentao.net/book/api/1198.html) |

**工时记录接口跨版本可用（2026-10-16 核实源码）**：开源版 `config/apiv1.php` 同样注册了 `$routes['/tasks/:id/estimate']`，条目文件 `api/v1/entries/taskrecordestimate.php` 存在（**全小写**命名）。该方法内部按 edition 自动分派：

```php
$issetEffort = $this->loadModel('effort') ? true : false;
if($issetEffort) $control = $this->loadController('effort', 'createForObject');   // 企业版有 effort 模块
else             $control = $this->loadController('task', 'recordWorkhour');       // 开源版走任务记工时
```

所以「写工时」不是企业版专属能力，**同一个接口两端都可用**，无需按版本降级。

登录不携带旧Token，其他开放接口请求使用Token头。按操作混用版本，不自动切换写接口重试。新建、修改、完成、关闭任务见 [任务操作](任务操作.md)，须单独预览确认。

## 链路选择：REST 优先，页面链路只做补充（2026-10-16 定稿）

禅道有两类入口，契约强度差别很大，取舍规则如下：

| 对比项 | REST（`/api.php/v1·v2/…`） | 页面链路（`{module}-{method}-{args}.json·html`） |
|---|---|---|
| 版本承诺 | 有：v1 ≥ 16.5、v2 ≥ 21.7.8 | **无**，随时可能变 |
| 与 edition 的关系 | 基本无关 | **受 edition 门控**，商业版模块在开源版不存在 |
| 公开文档 | 有 | 无，只能读源码或抓包 |
| 返回值 | 结构化 JSON | 页面级 JSON，常需二次解析（如 `data` 是二次编码的字符串） |

**四条规则**

1. **能用 REST 就用 REST。**
2. 页面链路**只用于「REST 覆盖不到 **且** 属于核心功能页面」**的场合。本技能目前仅三处，且都已对开源版源码逐个验证存在：
   - `/my-work-bug-{scope}.json` —— 「我的地盘 → 我的 Bug」。REST 里没有「我」这个资源，这个视角拿不到。
   - `/my-work-task-assignedTo-*.json` —— 取当前用户的候选任务，**一次请求即带出所属执行与执行名**。
   - `/bug-resolve-{id}.html` —— 取「解决版本」的合法值全集；虚拟版本 `trunk` 只在这个表单里出现。
3. **绝不用页面链路读写商业版专属模块**（如 `effort`）——那类页面在开源版会 404。（原先取候选任务用的 `/effort-batchCreate-*` 正因此被弃用。）
4. 页面链路失败同样**如实报错，绝不静默返回空**；结构不符时终止并说明，避免把「没读到」当成「没有」。

**为什么不做整体通用化**：REST 是**资源视角**（按产品 / 项目 / 执行组织），页面链路 + REST 混用才覆盖得了**人的视角**（「我的 Bug」「我这周的任务」）。纯 REST 的做法做不到「我现在有多少 Bug」这类问题——第三方 `zentao-nl-collaboration` 正是因此要求先选产品。所以补功能应顺着人的视角补，而不是把 REST 用全。

**页面链路失败时为什么不做自动 REST 回退（2026-10-16 实测）**：「我的 Bug」「我的任务」两条页面链路在 REST 里**没有等价入口**——实测 `v1/tasks`、`v2/tasks`、`v2/my/bugs`、`v2/my/tasks` 全部返回 **403**，`v2/bugs` 返回的是浏览页元数据（`title`/`products`/`browseType`/`modules`…）而不是 Bug 列表。若自动改端点，拿到的是语义不同的数据（资源视角 ≠ 人的视角），属于「看似成功的错数据」。

因此脚本采用的降级方式是：**页面缺失（404）或无权（403）时明确报出「页面不可用」，并把能走通的替代路径写进错误信息**（Bug 列表改用 `query --entity bugs --product|--project|--execution`，候选任务改用 `projects` → `executions --project` → `tasks --execution` 手动定位）；**网络类故障（如 502）保留原文案**，不把「稍后重试」误导成「换个命令」。此前的「结构不符即报错停止」保留不变——宁可报错，也不静默返回空。

## 当前候选任务

`zentao.py candidates` 读取 `/my-work-task-assignedTo-0-id_desc-0-{每页}-{页码}.json`（站点根路径，不加 `/api.php/`），即「我的地盘 → 我的任务」页面。使用 V2 登录保存的 Cookie，不能仅使用 Token。

站点返回 `{status, data, md5}`，`data` 是**需再次解析的 JSON 字符串**，其中 `tasks` 为任务数组，每条含 `id`、`name`、`execution`、`executionName`，另带 `status`、`left`。总数取 `data.pager.recTotal`。脚本逐页读取、按任务编号去重，并核对最终条数与总数一致；**结构不符或数量不符必须报错，不能视为没有任务**。

> 历史：原实现读「新增日志」页 `/effort-batchCreate-YYYYMMDD.html` 并解析 HTML 取 `objectType[]` 与 `executionTask`。该页属于 `module/effort/`，**开源版不存在**，会导致日志流水线在第一环断掉。改用「我的任务」后开源版同样可用，且结构化 JSON 比 HTML 稳定、一次即取到任务与执行名。

项目列表使用 status/page/limit；执行和任务列表使用 status/pageID/recPerPage。解析 pager.recTotal/pageTotal 并检查重复记录和总数。为历史关联默认 all；用户例子为 undone/unclosed，实例若不支持all须适配。分页检测重复页、提前空页。

## 批量载荷

```json
{
  "date": ["2026-09-07", "2026-09-08"],
  "work": ["完成接口联调并验证。", "修复输入校验并自测。"],
  "consumed": [8, 8],
  "left": [16, 8]
}
```

同请求只针对一个任务，四组等长数组逐项对应。用户原示例多了一层花括号且含注释，脚本改为单层合法JSON。left 是每条登记后剩余。登记可能激活任务，须预览确认；写入后的工时可在**对应任务的详情页**查看与修改（企业版另有「地盘 → 日志」汇总视图，开源版没有该视图）。

## 响应适配状态

读取器接受列表、指定列表键、data包装或按数字编号组织的对象。官方日志示例为 effort 下按日志ID组织的对象，已适配该结构及空 effort 对象；同时兼容 estimates 列表。单条要求 date/work/consumed/left/account，有 objectID/objectType 时核对确为当前任务。未知结构报错，不当作零条。

任务详情需要 id/name/execution/left/status/assignedTo；assignedTo 可以是账号或含account的对象。分页参考[官方v1任务列表响应](https://www.zentao.net/book/api/715.html)，v2形态需实例验证。

批量数组形态依据公司接口样例实现，尚需真实实例验证。响应不同则取得脱敏样例后适配，不跳过校验。

首次实用：外部鉴权→本人身份→执行/任务详情→历史日志→完整预览→用户确认→提交并回查。核实任务详情页的工时记录、余额和状态是否符合预期。

401重新登录；其他错误分别处理，不打印可能回显凭据的原始错误。写结果不明不重试。没有已确认事务、幂等键或版本条件，本地检查不能保证跨机器并发严格只写一次。

## 当前用户 Bug 页面（只读）

GET `<站点>/my-work-bug-{scope}.json?zin=1`，使用登录 Cookie；`scope` 为 `assignedTo`、`openedBy`、`resolvedBy` 或 `closedBy`，默认 `assignedTo`。站点返回 `{status, data}`；`data` 可能是需再次解析的 JSON 字符串，`bugs` 可能是按编号索引的对象或空数组。实际总数取 `data.pager.recTotal`，`data.recTotal` 只是页面参数；页码和每页条数分别取 `data.pageID`、`data.recPerPage`。下一页使用路径式路由 `/my-work-bug-{scope}-0-id_desc-0-{recPerPage}-{pageID}.json?zin=1`，因为该站点会忽略查询参数中的 `pageID`。脚本校验页码、总数、每页数量和每条记录在所选 `scope` 字段中的当前账号，再输出精简结果。该路径是页面内部协议，不保证跨版本兼容，格式不符不能视为空列表。指派给我不等于全部相关缺陷；展示状态，不将未确认当成未解决。

## Bug REST 接口

使用当前登录令牌；写操作均先预览、确认，再读详情回查。不提供删除 Bug 接口。

| 操作 | 方法及路径 | 说明 |
|---|---|---|
| 按名称查找产品 | GET v2/products | `browseType=all`、`recPerPage`、`pageID`，全量分页后匹配名称 |
| 产品 Bug 列表 | GET v2/products/{productID}/bugs | `browseType=all`、`recPerPage`、`pageID` |
| 项目 Bug 列表 | GET v2/projects/{projectID}/bugs | 同上 |
| 执行 Bug 列表 | GET v2/executions/{executionID}/bugs | 同上 |
| Bug 详情 | GET v2/bugs/{bugID} | 读取 `bug` 对象 |
| 创建 Bug | POST v1/bugs | 字段 `product`（产品编号）、`title`、`openedBuild` 必填；实测 v2 `POST /bugs` 用 `productID` 会创建出产品为空的 Bug，故改走 v1 |
| 修改 Bug | PUT v1/bugs/{bugID} | 仅发送明确修改的字段；实测 v2 对指派等字段可能返回空体却不落库。**站点会把未提供的字段重置**（实测 `assignedTo` 被清空），写后由脚本逐项核对未请求字段是否漂移 |
| 确认 Bug | POST v1/bugs/{bugID}/confirm | v2 文档未列此操作，使用 v1 |
| 解决 Bug | PUT v2/bugs/{bugID}/resolve | `resolution`（解决方案）与 `resolvedBuild`（解决版本）均为**服务端必填** |
| 关闭 Bug | PUT v2/bugs/{bugID}/close | 只允许已解决状态 |
| 激活 Bug | PUT v2/bugs/{bugID}/activate | 只允许已解决或已关闭状态；`openedBuild` 必填 |
| 上传附件 | POST v1/files | multipart/form-data，字段 `imgFile`，返回 `{id, url}`；内嵌到重现步骤使用返回的 `url`。**官方 v1 手册未收录该接口**，依据是禅道社区官方回复加 2026-10-09 本站点实测（未传文件时返回 400「文件格式不在规定范围内」，说明路由可用）。官方文档中的 `POST v2/files`（v22.0+，字段 `file`/`objectType`/`objectID`）在本站点返回 403，`GET v2/files/{id}` 同样 403 |

v2 列表与详情已在当前站点只读验证；v1 创建、修改、确认已在当前实例写入并回查。问题清单记录了 v2 解决、激活接口返回规范 JSON，以及激活缺少 `openedBuild` 会被拒绝；未提供激活成功后详情状态回查记录，因此激活的端到端成功仍待验证。v2 关闭在当前账号下返回 403，可能需要额外权限。其他账号或站点仍须以实际响应及写后详情回查为准；不能把本地预览当作远端写入成功。

### 解决 Bug 的字段要求（2026-10-12 实测）

- `resolution` 合法值：`bydesign`、`duplicate`、`external`、`fixed`（已解决）、`notrepro`、`postponed`、`willnotfix`。
- `resolvedBuild`（解决版本）**网页表单显示为可选**（页面 JS 的 `requiredFields` 只列 `resolution`），但**接口强制校验**：缺失时返回 `{"message":{"resolvedBuild":["『解决版本』不能为空。"]},"status":"fail"}`。脚本会把该响应归为笼统的"业务失败"，需按下方办法定位。
- 取服务端失败说明：`auth.request(base, 'PUT', 'v2/bugs/{bugID}/resolve', token, body, allow_failure=True)` 直接调用并读取返回的 `message`；**前提是先用只读回查确认上一次未写入**，否则即为盲目重发。解决成功后 `assignedTo` 会被清空，属正常表现。
- **解决版本已自动化，不必再手填**：`prepare` 时若 `resolvedBuild` 缺失，脚本自动按规则补齐并在 `notice` 中标注来源与可选值。

### 构建与解决版本查询（2026-10-12 实测可用）

| 用途 | 方法及路径 | 说明 |
|---|---|---|
| 项目构建列表 | GET v1/projects/{projectID}/builds | 需 `limit`；返回 `id`、`name`、`product`、`execution`、`date`。`?product=` / `?productID=` 过滤参数**无效**，仍返回全部，需客户端按 `product` 字段自行筛选 |
| 执行构建列表 | GET v1/executions/{executionID}/builds | 同上，条数更少（仅该执行） |
| 解决版本合法取值 | 读网页 `/bug-resolve-{bugID}.html` 的 picker `items` | **唯一包含虚拟版本 `trunk`（主干）的来源** |
| 脚本命令 | `zentao.py builds --project N`／`--execution N` | 输出构建列表 |
| 脚本命令 | `zentao.py resolve-builds --bug N` | 输出合法取值 + `recommended` 推荐项 |

**关键结论：`trunk` 不在构建接口返回里**（它是禅道的虚拟版本，语义为"主干"），只在解决表单选项中存在。因此：

- 解决版本推荐规则：**`openedBuild` 有值且在选择列表内 → 用它；否则回退 `trunk`**（`resolve-builds`/`prepare` 均按此自动判定）。
- v2 的 `/v2/builds`、`/v2/products/{id}/builds` 在当前账号下返回 **403 无权限**；v1 的 `/v1/builds`、`/v1/products/{id}/builds` 返回 400/404，均不可用。


## 测试单与用例接口（以开源版条目源码 + 实测核对）

**测试单**

- `POST v1/testtasks` 或 `POST v1/projects/{projectID}/testtasks`——**`project` 只认路径或 query 参数**，放 JSON body 会被忽略并报 `need project id!`。
- 必填四关联 **project、product、execution、build** 加 **name、begin、end**；服务端还会核对「执行属于该产品与该项目的关联、构建属于该产品」，不满足只回一句 `error execution id!` / `error build id!`。
- `GET v1/testtasks` 列表、`GET v1/testtasks/{id}` 详情（详情含该测试单下各用例的执行结果）。
- **修改必须走 v2**：`PUT v2/testtasks/{id}`。v1 的 `testtask.php` 只实现 `get()` 与 `delete()`，`PUT v1/testtasks/{id}` 返回 **200 且响应为空**——静默假成功。v2 是**整份覆盖**：没传的字段会被静默清空（`execution`、`owner` 等），必填的 `name`/`build`/`begin`/`end` 缺失则直接报错；产品字段写作 `productID`（v1 的 `product` 也认），`type` 接受数组或字符串，`execution` 可空，`project` 虽未列在文档请求体里但确实可写。
- `GET v1/testtasks/{id}`（编号不存在时）返回 **400** 并带一句「请检查测试单的产品是否与迭代相关联」，而非 404。

**用例**

- `POST v1/testcases`（product 放请求体）——**路径式 `POST v1/products/{id}/testcases` 返回 403**：两个路由指向同一个条目类，但权限判定不同。
- 必填 **product、title、type、pri、steps**；`steps` 是数组，每项 `desc`/`expect`/`type`（`step`/`item`/`group`）。
- `PUT v1/testcases/{id}` 修改，可选 `branch`、`script`、`keywords`；给出 steps 会整体替换。
- `GET v1/testcases/{id}` 详情含 steps；编号不存在返回 404。

**权限**：测试单的写通常属测试角色；用例的创建与修改通常需测试角色或管理员授权（开发账号常见无权限）。**注意探测陷阱**：`POST v1/testcases` 缺 product 时返回 400「Need product id.」——必填校验先于权限检查，只看这个 400 会把「无权限」误判成「有权限」。
