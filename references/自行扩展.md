# 自行扩展

**什么时候该看这篇**

- 技能报错：接口返回 4xx/5xx、提示「字段与请求不一致」「找不到编号」，或某功能在你的禅道版本上不可用。
- 技能没覆盖：你想做的事在命令列表里找不到（例如批量指派需求、查执行成员、把需求关联到产品计划、按版本统计 Bug）。
- 你的禅道版本与文档矩阵不同，某条接口行为不一样。

**本篇的定位**：技能不追求把禅道全部接口封完（那既不现实也没必要）。它是一个**可以改的起点**——缺口出现时，照着下面三步自己加，比等更新快。**遇到报错不要凭猜测硬调接口**，先按本文走一遍。

---

## 一、先看边界：哪些该改，哪些不要碰

| 建议改                            | 说明                                             |
| ------------------------------ | ---------------------------------------------- |
| `scripts/routes.py`            | 只读查询表。**加一个实体通常只加一行**                          |
| `scripts/actions.py` 的 `SPECS` | 写操作字段表。字段名、类型、必填、关联预检都在这张表里                    |
| 新建 `scripts/xxx_actions.py`    | 新的写流程，照 `test_actions.py` 的写法（只声明字段表 + 两个包装函数） |
| `scripts/zentao.py`            | 注册子命令与分发                                       |

| 不要碰                                         | 原因                     |
| ------------------------------------------- | ---------------------- |
| `scripts/auth.py`、`scripts/local_cipher.py` | 认证与密钥保护。改错会泄露凭据或造成静默降级 |
| 两阶段机制（预览 → 确认 → 单次写入 → 回查）                  | 这是防误写、防重复提交的唯一保障       |
| 删除接口                                        | 有意不提供：公开技能不放无约束的删除     |

## 二、官方文档在哪

| 文档                           | 地址                                          | 用途                                                         |
| ---------------------------- | ------------------------------------------- | ---------------------------------------------------------- |
| 禅道二次开发手册（**v1 与 v2 都在这一本里**） | <https://www.zentao.net/book/api/664.html>  | 按实体查接口：方法、路径、请求体、必填                                        |
| APIv2.0 使用教程                 | <https://www.zentao.net/book/api/2309.html> | 认证流程：`POST /tokens` 取 token，后续请求把 token 放 header；401 表示没带对 |

**两个使用提醒**：

1. **v1 手册本身有标注错误**（例如某些接口的 GET/PUT 标反了）。文档与实例冲突时，**以实例实测为准**，并把差异记下来。
2. **手册没写的字段也可能有效**。例如 v2 修改测试单的请求体没列 `project`，但实测 `project` 是可写字段（传错编号会报 `Project does not exist.`）。

## 三、v1 与 v2 可以混用——这是关键

同一个实体，**读和写可能分属不同版本**，甚至只有一边有。所以不要假设"选了 v1 就全用 v1"。

实例证据（均来自实测）：

| 场景              | 只能用 v1                                 | 只能用 v2                                                                       |
| --------------- | -------------------------------------- | ---------------------------------------------------------------------------- |
| 测试单**创建**       | `POST v1/projects/{project}/testtasks` | —                                                                            |
| 测试单**修改**       | —                                      | `PUT v2/testtasks/{id}`（v1 没有 PUT，且 `PUT v1/testtasks/{id}` 返回 200 空响应，是假成功） |
| 需求**正文** `spec` | `GET v1/stories/{id}`（v2 详情不含正文）       | —                                                                            |
| 统计报表            | `GET v1/reports`（v2 同名端点 403）          | —                                                                            |
| Bug 列表          | —                                      | `GET v2/{products\|projects\|executions}/{id}/bugs?browseType=all`           |

**怎么判断该用哪个**：

1. 先按版本门槛初筛：v1 约 ≥ 16.5，v2 约 ≥ 21.7.8（企业版 12.7 同代）。你的版本低于门槛就只能走另一边。
2. 再看能力：v1 偏「业务动作」（如 `finish`/`activate`/`resolve`），v2 偏「资源 CRUD」。
3. 两个都有时，**优先 v1**——它的行为在更多版本上被验证过；但 v2 返回的字段往往更规整。
4. 不确定就各发一次**只读 GET**，比较返回结构与字段名，再决定。

**同一实体在 v1/v2 的字段名可能不同**：测试单的产品在 v2 文档写作 `productID`，v1 用 `product`。混用时必须在提交前做一次字段名映射（参考 `test_actions.py` 的 `update_wire`）。

## 四、三种常见的扩展

### 1. 加一个只读实体（最简单）

在 `scripts/routes.py` 的 `ENTITIES` 里加一行：

```python
"builds": {
    "label": "构建",
    "collection": "builds",
    "detail": "v1/builds/{id}",                       # 详情写实测可用的那个版本
    "summary": ("id", "name", "product", "project", "date"),
    "lists": (
        # arg 是必填的范围参数；paging 取 page（v1）、pageID（v2）或 none（一次全量）
        {"arg": "project", "path": "v1/projects/{project}/builds", "paging": "page"},
    ),
},
```

（上面是**示例形态**，端点未经逐个实测；加之前先用 `query --entity ...` 走一遍确认返回结构。）

然后用 `entities` 自省、用 `query --entity builds --project 8` 试。**范围编号要能验证存在**——接口对写错的编号常常静默返回别的数据。

### 2. 加写操作

在 `scripts/actions.py` 的 `SPECS` 里加一张字段表（参考现有 `testtask`、`story`），字段类型有 `TEXT`/`TEXTS`（文本或文本数组）/`DATE`/`ID`/`IDS`/`ACCOUNT`/`ENUM`/`INT`；`required` 决定创建或修改时必填；`scope` 声明关联编号需要预检。

若修改端点与详情端点不在同一版本，用 `update_endpoint`；若接口是「整份覆盖」语义（见下条），用 `update_fill`。
整份覆盖提交需要核验全部提交字段时，再启用 `verify_full_body`，不能只检查用户点名修改的字段。
修改时必须保持不变的关键字段用 `monitor_fields` 声明；公共骨架会在写后对比修改前后的值，发现未请求字段漂移时停止报成功并保留收据。

### 3. 加一条业务流水线

照 `test_actions.py` 的结构新建一个模块：一张 `SPECS` + `prepare()`/`execute()` 两个包装函数，然后在 `scripts/zentao.py` 注册 `xxx-prepare` / `xxx-submit`。流程代码不要复制——骨架已经在 `actions.py` 里。

## 五、六条必须遵守（每条都由一次真实事故换来）

1. **写操作必须两阶段**：预览 → 用户确认 → 单次写入 → 回查。写完不查等于没写。
2. **关联编号先在预览阶段验证存在**。接口对写错的编号往往不报错，而是返回别的数据或按 0 处理。
3. **未知字段会被静默忽略**。拼错一个字段名，接口照常返回成功，但那个字段根本没生效。字段名一律以源码或实测为准。
4. **整份覆盖型 PUT 必须先把当前值铺满**。v2 修改测试单就是这种语义：只传 name 时，`execution` 与 `owner` 会被静默清成 0 和空串。`update_fill` 就是干这个的。
5. **200 不等于成功**。有些接口成功返回真数据，有些返回空响应，有些即使失败也返回 200（业务失败在 body 的 `status` 里）。所以一律**回查实际数据**，不信返回码。
6. **契约不全就停，不许猜**。缺 method、缺路径、缺必填、缺权限要求中任何一项，就停在这里查清楚；猜出来的请求即使成功也是错数据。

## 六、改完怎么自测

按这个顺序，**不要一上来就写真实数据**：

1. **只读探测**：详情、列表能不能拿到，字段名与你预期是否一致。
2. **错误分支**：编号不存在、编号缺失、字段不支持、必填缺失、关联不匹配、无权限（403）。这些分支必须给出可读提示，不能是裸的 HTTP 状态码。
3. **小范围真实写入**：用带标记的测试数据（例如名称前缀「（技能验证）」），便于识别。
4. **先确认可清理性**：自己有没有删除权限。没有的话，这条测试数据会留在用户实例里（真实教训）。
5. **回查**：逐字段核对，包括**本次没请求的字段**有没有被意外清空。
6. **回归**：跑一遍原有的只读命令，确认没被改坏。
7. **换行用 LF**：新增文件保存为 LF。仓库 `.gitattributes` 已设 `eol=lf`，用 CRLF 保存会让整份文件在 diff 里变红（`.bat` / `.cmd` / `.ps1` 例外，规则里已单独设为 CRLF）。

## 七、报错时先看这些

| 现象             | 先看                                                                     |
| -------------- | ---------------------------------------------------------------------- |
| 「找不到编号」/ 404   | `references/禅道接口说明.md` 的端点清单；注意 404 也可能是「记录不存在」而非「路由不存在」               |
| 「记录不存在」被报成权限问题 | v2 用 `{"status":"fail","message":"X does not exist."}` 表达不存在（HTTP 200） |
| 字段改了但没生效       | 字段名拼错被静默忽略；或该字段在修改接口里是整份覆盖语义                                           |
| 403            | 权限不足。**先补齐必填再看返回码**——必填校验可能先于权限检查执行                                    |
| 返回全量数据而非你筛选的   | 参数不被支持（禅道常见：非法范围参数退化成返回全部）                                             |

如果仍解决不了，把 **HTTP 状态 + 服务端原文 + 请求路径**记下来——这三样是定位问题的全部依据，缺一样就只能靠猜。
